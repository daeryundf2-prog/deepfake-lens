# GUI 재설계 적대적 리뷰 4차 (gui-redesign d613df3)

## 판정: 수정 후 머지 (서명 무결성 문제는 없음, 409 화면 처리 K-1·K-2를 같은 PR에서 고칠 것)

머지(79894e6)는 양쪽 동작을 보존했습니다. 0단계 R19-3·R19-8·R19-10·R19-11·R19-13은 HEAD에서 직접 재현해 모두 유지됨을 확인했습니다. GUI 쪽 G·H·J 수정도 손상된 것이 없습니다. 원고 측(및 의뢰 측 없음) 웹 산출물은 phase0ref 서버와 비교해 서명·문서번호·시각·모델 프로필 경로 외에는 같습니다. 증거설명서 PDF 텍스트는 diff 0입니다.

R19-13의 409는 두 서버(stdlib 8821, FastAPI 8824)에서 서명되는 다섯 형식(json/html/pdf/evidence/evidence-json) 모두에서 동작합니다. 파일 교체, 압축 구성원 교체, 삭제, 내용만 바뀐 경우, 파일이 심볼릭 링크로 바뀐 경우, dedupe 원본 변경이 모두 409이고 아무것도 서명되지 않았습니다. 3차의 J-1(High)은 닫혔습니다.

남은 문제는 d613df3이 새로 만든 GUI 409 처리에 있습니다.
- **K-1:** 409 응답과 그 표시가 어느 검사에 대한 것인지 묶여 있지 않습니다.
  - 내보내기가 진행 중일 때 다른 폴더를 검사하면, 늦게 도착한 409가 새 검사의 같은 이름 행에 "검사 뒤 바뀜"을 찍습니다. 이때 "다시 검사" 버튼은 새 폴더를 채웁니다.
  - 다시 검사해 내보내기가 성공한 뒤에도 "생성 거부 … 다시 검사하십시오" 오류가 "이전 검사" 표시 없이 그대로 남습니다.
- **K-2:** 409의 이유와 "다시 검사" 버튼이 화면 맨 위의 오류 영역에만 나옵니다. 그런데 내보내기 버튼은 시험한 모든 해상도(1920×1080 포함)에서 첫 화면 아래에 있어서, 버튼을 누른 사용자는 오류를 볼 수 없습니다. 버튼 옆에는 "…를 만들지 못했습니다."만 보입니다.

둘 다 잘못된 문서를 서명하게 하지는 않습니다. 다만 이 도구가 지켜야 할 "무엇이 왜 안 됐는지 정직하게 말한다"를 어깁니다. K-1은 사실이 아닌 경고를 표시하고, K-2는 이유를 숨깁니다. 수정은 각각 몇 줄입니다.

## 새로 찾은 문제

### K-1 (Med) — 409 표시가 어느 검사에 대한 것인지 묶여 있지 않음: 다른 검사의 행에 표시가 붙고, 고친 뒤에도 거부 오류가 남음
- **재현 A (늦게 도착한 409):**
  1. 폴더 big(a1111.png 포함 301개)을 검사하고, 디스크의 big/a1111.png를 다른 내용으로 바꿉니다.
  2. 감정서 화면에서 "서명된 JSON"을 누릅니다. 큰 폴더의 재분석이 오래 걸리는 상황은 `/api/report` 응답을 8초 늦추는 fetch 래퍼로 흉내 냈습니다.
  3. 그 사이 검사 화면에서 폴더 small(같은 이름의 a1111.png, 바뀌지 않음)을 검사합니다. 내보내기는 검사 시작을 막지 않습니다.
  4. small 결과(2행)가 먼저 표시되고, 이어서 big의 409가 도착합니다.
  - 결과: small의 a1111.png 행에 붉은 줄과 "검사 뒤 바뀜 — 다시 검사"가 붙고, 상세 창은 "서버가 다시 분석해 보니 검사 때와 다릅니다"라고 말합니다(`changedPaths = ["a1111.png"]`). 오류의 "다시 검사" 버튼은 `lastScanRoot`, 즉 small을 채웁니다.
- **재현 B (고친 뒤에도 남는 오류):** g1에서 409를 받고 "다시 검사"를 누른 뒤 검사하고 다시 내보냈습니다.
  - 결과: 표시는 지워지지만, "검사 뒤 바뀜 증거설명서(PDF) 생성 거부 … 다시 검사하십시오 … a1111.png(조작·생성 근거 있음 → 판단 불가)" 오류 두 개가 "이전 검사" 표시 없이 그대로 남습니다. 바로 아래 export-note에는 "서명된 JSON를 내려받았습니다."가 표시됩니다.
  - 전혀 다른 폴더(huge)를 검사하는 동안에도 남아 있고, 그때 "다시 검사"를 누르면 huge가 채워집니다.
- **원인:** `exportReport`가 요청 시점의 검사(`scanGeneration` 또는 결과 식별자)를 기억하지 않습니다. `markChangedRows`는 응답이 올 때 화면에 있는 결과에 경로 이름만으로 표시를 붙입니다. `showError(…, false, …)`는 H-10 규칙에 따라 `data-scan`이 없으므로 `retireErrors()`의 대상이 아닙니다. 성공한 내보내기도 같은 구조라서, 이전 검사의 보고서가 새 결과가 표시된 뒤에 내려받아질 수 있습니다(이 부분은 원래 있던 동작).
- **영향:** 변경되지 않은 파일을 "검사 뒤 바뀜"이라고 표시합니다. 고친 뒤에도 "생성 거부"를 계속 보여 주므로, 검사관은 이 도구의 경고를 무시하는 습관을 들이게 됩니다. 서명되는 산출물 자체는 영향받지 않습니다.
- **수정:**
  - 요청 전에 `const gen = scanGeneration`을 잡아 두고, 응답 때 다르면 표시·오류·다운로드를 버리고 "이전 검사에 대한 응답이라 무시했습니다"만 알립니다.
  - 409 오류 상자에 `data-scan`(또는 전용 표지)을 달아 `processResults`·`retireErrors`에서 "이전 검사"로 바꾸거나 지웁니다. 같은 내용이 반복되면 상자를 하나로 합칩니다.
  - 시험을 추가합니다. smoke에서 다시 검사 → 내보내기 성공 뒤 "생성 거부" 상자가 없거나 `err-old`인지 확인하고, node 시험에서 세대가 바뀐 뒤의 응답이 무시되는지 확인합니다.

### K-2 (Med-Low, 접근성·정직성) — 409 이유와 "다시 검사"가 보이지 않는 곳에 뜸
- **재현:**
  - 1920×1080: 감정서 화면의 exp-evidence는 `top=1428px`(문서 높이 1539)로 첫 화면 아래에 있습니다.
  - 1366×768: 버튼을 화면 가운데로 스크롤해 누르면 오류 상자는 `top=-730px`입니다.
  - 375×812(어두운 모드): `top=-1697px`입니다.
  - 세 경우 모두 초점은 버튼에 남고, 버튼 바로 아래 export-note에는 "증거설명서(PDF)를 만들지 못했습니다."만 보입니다(스크린샷으로 확인). `#error-region`은 `position: static`, `aria-live=assertive`입니다.
- **영향:** 화면 낭독기를 쓰지 않는 사용자는 이유(어느 파일이 어떻게 바뀌었는지)도, 해결 버튼도 보지 못합니다. 버튼을 다시 누르면 같은 상자가 계속 쌓이고, 4개 상한 때문에 다른 오류가 밀려납니다. 미리보기와 확인 목록도 409 뒤에 바뀌지 않아서, a1111.png가 여전히 "을 제2호증 조작·생성 근거 있음"으로 보입니다.
- **수정:**
  - export-note(또는 버튼 옆의 `role=alert` 상자)에 "검사 뒤 바뀐 파일 n개 — 내보내지 않았습니다"와 "다시 검사" 버튼을 둡니다.
  - 확인 목록에 필수 항목 "검사 뒤 바뀐 파일 n개(다시 검사 필요)"를 추가하고, 다시 검사 전까지 서명 형식 버튼에 그 이유를 표시합니다.
  - 오류 영역을 sticky로 만들거나 오류 상자로 스크롤하는 방법도 됩니다.

### K-3 (Low, 접근성) — "다시 검사"를 누르면 초점이 "검사 시작"이 아니라 제목(H1)에 감
- **재현:** 409 오류의 "다시 검사"를 클릭한 직후 `document.activeElement`가 `H1`입니다(`analyze-btn` 아님).
- **원인:** `rescanFolder()`가 `navigate('scan')`을 초점 대상 없이 부릅니다. 이어서 `$('analyze-btn').focus()`를 하지만, 나중에 실행되는 `hashchange`가 `showView(…, pendingFocus=null)`로 제목에 초점을 옮겨 덮어씁니다.
- **수정:** `navigate('scan', $('analyze-btn'))`로 바꿉니다. smoke에 `document.activeElement.id === 'analyze-btn'` 확인을 추가합니다.

# GUI 재설계 적대적 리뷰 2차 (gui-redesign 4fb7d25)

## 판정: 수정 후 머지

1차 지적 열 건 가운데 가장 무거운 G-1(서명 산출물에서 행이 빠지던 문제)은 실제로 닫혔습니다. 서버 산출물(서명 JSON·HTML·감정 PDF·증거설명서 PDF)은 선택과 상관없이 모든 행과 전체 요약을 싣습니다. 부록(`excluded_by_selection`)은 서명에 포함되어 행 삭제·순서 변경·해시 수정·키 삭제가 모두 `tampered`로 검출됩니다. 새 인자를 쓰지 않은 증거설명서는 base와 MD·JSON 바이트, PDF 텍스트까지 동일합니다. stdlib 서버와 FastAPI 서버의 동작도 같고, 전체 게이트도 통과합니다(rc=0).

다만 G-1 수정이 새 결함을 만들었습니다. 증거설명서 미리보기의 호증 번호가 실제로 서명되어 나오는 PDF의 호증 번호와 다릅니다(H-1). rev1에서는 고른 행을 미리보기 순서대로 보냈기 때문에 두 번호가 같았습니다. 지금은 모든 행을 서버 순서로 보내고, `exhibit_paths`는 집합으로만 쓰입니다. 그래서 화면은 "을 제2호증 = evid.zip"이라고 보여 주는데 서명된 PDF에는 "을 제2호증 = evid.zip::inner/sd.png"로 찍힙니다. 법정에 내는 문서의 번호가 화면에서 확인한 것과 다르다는 뜻이고, 이 도구가 내세우는 "미리 본 것이 곧 나가는 것"이라는 정직성을 깨뜨립니다. 그 밖에 다음이 남아 있습니다.
- 미리보기에 실제 PDF에 없는 "결론 요약" 문장과 "검사의 한계" 절이 있습니다. 그 문장은 단서가 있는 행까지 "판단할 근거가 없었으며"라고 씁니다(H-2).
- 피고 측 문구가 서식 전체에서 일관되지 않습니다(H-3).
- 기본 선택으로 만든 증거설명서에서 단서 행의 근거가 빠지고, 부록에는 결론 라벨만 남습니다(H-4).
- 검사가 끝나면 다른 화면에서 입력 중이던 사용자를 사건 대장으로 끌고 가며 초점을 빼앗습니다(H-5).

H-1과 H-2는 작은 수정으로 고칠 수 있으므로 판정은 "머지 불가"가 아니라 "수정 후 머지"입니다. 둘 다 고치고 테스트를 붙인 뒤 머지하기를 권합니다.

## 새로 찾은 문제

### H-1 (High) — 미리보기 호증 번호와 서명된 증거설명서의 호증 번호가 다름 (G-1 수정이 만든 회귀)
- **재현:** hostile 폴더 검사 → 감정서 만들기 → 의뢰 측 "피고·피의자 측", 기본 선택(조작·원본성 근거)을 둡니다. A4 미리보기는 `을 제1호증 dalle.jpg / 을 제2호증 evid.zip / 을 제3호증 evid.zip::inner/sd.png`입니다. 증거설명서 PDF를 내려받으면(GUI가 보낸 요청을 그대로 썼습니다. `exhibit_paths`=["dalle.jpg","evid.zip","evid.zip::inner/sd.png"], items는 서버 순서) PDF 본문은 `을 제1호증 dalle.jpg / 을 제2호증 evid.zip::inner/sd.png / 을 제3호증 evid.zip`이고, 압축 파일 행은 "구성원별 근거는 을 제2호증(evid.zip::inner/sd.png) 참조"입니다.
- **원인:** 미리보기는 `selectedEntries()`를 `byVerdict`(결론 순위 → 단서·실패·근거 없음·참고 순위 → 이름)로 정렬해 번호를 붙입니다(gui.js:2091, 2180). 서버는 보낸 행 순서(= 스캔 결과 순서)에서 `item.path in exhibit_paths`인 행만 걸러 번호를 붙입니다(evidence_statement.py:448, 453). `exhibit_paths`는 frozenset이라 GUI가 보낸 순서가 버려집니다. rev1은 고른 행만 미리보기 순서로 보냈기 때문에 번호가 같았습니다.
- **영향:** 검사관이 화면에서 확인하고 준비서면에 인용한 "을 제2호증"이 제출 문서에서는 다른 파일입니다. 판단 불가 칸까지 고르면 거의 모든 번호가 어긋납니다(UNDET_ORDER는 서버 순서에 없는 개념입니다). 올린 파일 행은 미리보기에서 호증 번호를 받지만, 서버에서는 서명 제외 행이 되어 호증이 아닙니다. 그 뒤 번호가 모두 밀립니다.
- **수정:** `exhibit_paths`를 순서 있는 목록으로 보고, 서버가 그 순서대로 번호를 붙이게 합니다(스캔에 없는 경로는 400). 또는 GUI가 서버 순서로 미리보기를 그리게 합니다. 올린 파일 행은 미리보기에서도 호증에서 빼거나 "서명 제외"로 표시합니다. 테스트를 붙입니다: gui_smoke에서 A4의 (호증, 파일) 목록과 PDF 텍스트의 (호증, 파일) 목록이 같아야 하고, 판단 불가 칸 포함·압축 파일 포함 경우도 봅니다.

### H-2 (Med) — A4 미리보기가 실제 PDF에 없는 내용을 보여 주고, 그 문장이 G-2 수정과 모순됨
- **재현:** 위와 같은 경로입니다. 미리보기에는 "1. 결론 요약 — 22개 파일 중 3개에서 … 18개는 판단할 근거가 없었으며 이는 원본임을 뜻하지 아니한다."와 "2. 검사의 한계"가 있습니다. 실제 PDF(pymupdf 텍스트 추출)에는 "결론 요약", "판단할 근거", "검사의 한계"라는 글이 하나도 없습니다. 대신 PDF에 있는 "기록되지 않은 파일: 2개(압축 거부 멤버 1, 미지원 1)"와 "무결성/해석 고지"는 미리보기에 없습니다.
- **영향:** 미리보기가 산출물과 다릅니다. 같은 화면 헤드라인은 "단서만 있음 3"이라고 하는데 미리보기 문장은 그 세 개까지 "판단할 근거가 없었으며"라고 씁니다. 1차 G-1에서 지적한 "미리보기 ≠ 산출물"이 형태만 바뀌어 남아 있습니다.
- **수정:** 미리보기는 서버 서식에 실제로 있는 절만 그립니다(사건 칸, 서증 목록, 기록되지 않은 파일, 부록, 고지). 요약 문장을 둔다면 서버 서식에도 똑같이 넣고, 판단 불가 분할을 반영합니다.

### H-3 (Med) — 피고(피의자) 측 문구가 일관되지 않음
- **증거:**
  - 감정 보고서 PDF: `exportPayload`가 `exhibit_no='갑 제        호증'`으로 고정합니다(gui.js:2212). `submitter_side=defendant`로 보내도 PDF 텍스트는 `['갑 제        호증']`입니다.
  - 증거설명서 PDF·MD: 원고 자리 기본값이 "(의뢰사 상호명 입력) 귀하"(webapp_api.py:1876, cli_parser)입니다. 피고 측일 때는 의뢰사가 피고인데 의뢰사 이름 자리가 원고 칸에 찍힙니다.
  - GUI 확인 목록: "의뢰인 또는 피고·피의자가 비어 있습니다"(gui.js:2101)가 원고 칸을 "의뢰인"이라고 부릅니다. 피고 측을 고른 화면에서도 같은 문구가 나옵니다.
  - 문서 사이 불일치: MD 머리말은 "피고(피의자)의 대리인은", PDF는 "피고(피의자)의 변호인은", 서명란은 양쪽 모두 "피고(피의자) 변호인"입니다.
  - 입증취지의 "관련 법조: 정보통신망법 제70조(벌칙 - 명예훼손) — 검토 참고"는 피고 측 제출에서도 그대로 붙습니다(원고 측 시각의 문구).
- **영향:** 법률 문서로서의 정합성이 떨어지고, 의뢰사 이름이 상대방 칸에 들어갈 위험이 있습니다.
- **수정:** 의뢰 측에 따라 감정 PDF 호증 접두어, 기본 자리표시(의뢰사 칸 위치), 확인 목록 문구, 머리말 호칭(대리인/변호인)을 한 곳에서 정합니다. 테스트도 그 결과를 고정하도록 바꿉니다.

### H-4 (Med) — 기본 선택의 증거설명서가 단서·실패 정보를 잃음 (base 대비 정보 손실) [0단계 회귀 가능성]
- **재현:** 기본 선택(조작·원본성만)으로 증거설명서를 만들면 mj.png·mj_copy1/2(Midjourney 단서), empty.png·truncated.png(검사 실패), meta.pdf(문서 메타데이터 "ChatGPT")가 모두 부록에 "— 판단 불가 — SHA-256: …" 한 줄로만 남습니다. base의 증거설명서는 모든 행을 서증으로 싣고, 행마다 "• 결정적 근거: …"·"• 검사 범위: …" 근거 줄과 실패 사유를 적었습니다.
- **영향:** 서명된 제출 문서만 받아 본 사람은 단서가 있었다는 사실도, 검사 실패로 판단하지 않았다는 사실도 알 수 없습니다. "왜 틀릴 수 있는지 말한다"는 원칙이 약해집니다.
- **수정:** 부록 행에 판단 불가의 종류(단서만 있음/근거 없음/검사 실패/참고 전용)와 단서·실패 한 줄 요약을 넣습니다. 또는 단서·실패 행은 기본 선택에 포함합니다. 미리보기 확인 목록에도 "부록 행 중 단서 n개·검사 실패 m개"를 경고합니다.

### H-5 (Med) — 검사가 끝나면 다른 화면에서 입력 중이던 사용자를 사건 대장으로 끌고 감 (접근성: 예기치 않은 문맥 변경)

### H-7 (Low) — 서버가 호증 0개짜리 증거설명서에 서명함

### H-9 (Low) — 업로드 검사가 결과 도착 전에 이전 결과의 프로비넌스를 덮어씀 (G-5 잔여)

### 이상 없음으로 확인한 공격
- **XSS:** 파일 이름(`<img src=x onerror=alert(1)>.png`, `evid.zip::inner/<i>x</i>.png`, RTL, 개행, NFD, 240바이트 이상 이름)과 메타데이터(PNG tEXt `<script>`, EXIF Software·ImageDescription, PDF title/producer `<script>`)를 넣고 38개 행 상세를 모두 열어 봤습니다. alert 0건, 주입된 on* 속성 0건이었습니다. CSP는 `default-src 'self'; script-src 'self'; … object-src 'none'; base-uri 'none'`입니다.
- **표시 이름 단사성:** `a\nb.png`(실제 개행)와 `a\\nb.png`(백슬래시)가 부록에서 구분됩니다.
- **잘못된 타입 요청:** `exhibit_paths`가 문자열·숫자 배열·dict이거나, `submitter_side`가 잘못된 값·숫자·배열·null이면 400이고 두 서버가 같습니다.
- **동시 실행:** 작업 두 개를 동시에 돌렸을 때 진행 필드(done/total/current)가 섞이지 않았습니다.
- **두 서버 응답:** 모르는 job은 404, `/api/stats`와 `/api/scan-status`의 필드는 두 서버가 같습니다.
- **접근성·대비:** 대비는 밝은 모드에서 진행 중 띠 17.8:1, "이전 검사" 머리 6.3:1, 단서 행 보조 문구 5.7:1, 어두운 모드에서 모두 6.9:1 이상입니다. 375px에서 네 화면 모두 가로 넘침이 없습니다. `prefers-reduced-motion` 규칙이 있습니다. env-more의 `aria-expanded`가 맞게 바뀝니다. 감정서 화면 Tab 순서가 자연스럽습니다.
- **base 대비 정보 손실:** 행 상세에 전체 sha256, 서버 결론 문장, 다음 확인, 출처 추정, 검사 범위가 모두 있습니다. base가 읽던 필드 중 없어진 것은 미보정 score 링(0단계에서 항상 0)뿐입니다.
